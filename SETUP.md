# Application setup

This project uses PHP with PDO MySQL. Configure the following environment variables for the PHP/Apache process:

- `DB_HOST`
- `DB_NAME`
- `DB_USER`
- `DB_PASSWORD` (may be empty for a local development database)

For a local XAMPP setup, edit `config.local.php` and set `DB_NAME`, `DB_USER`, and `DB_PASSWORD` to match your MySQL database. The local configuration currently targets `colm_registrar` with the common XAMPP account (`root` and an empty password). Environment variables take precedence when set. Do not use local development credentials in production, and do not share or commit real database credentials.

## Database setup

For a **new, empty database**, import `database/schema.sql` once. It is the complete, data-free baseline for the current application, including staff/student accounts, document requests, academic records, roster imports, and request history. Then run `database/seed_documents.sql` and `database/migrate_email_templates.sql` once. The latter creates or updates the default email templates. Add the first administrator through an approved database administration process and configure the course/year catalog in **Courses**; never copy live account or request rows into a clean install.

For an **existing database**, do not import `schema.sql` over it and do not run every migration in filename order. Migrations are one-time upgrades for different historical schemas, not a general cleanup routine. Inspect the existing table/column layout, back it up, and apply only the missing migration branch. Apply `database/migrate_admin_audit_events.sql` once for the administrator audit log and `database/migrate_staff_password_security.sql` once for forced first-login password changes and email-verification password recovery. Check whether the relevant tables and column exist before applying these migrations.

Administrators can manage personnel from the **Staff** page. Create an account with a full name, role, and email; the portal emails a one-time temporary password and activates the account only after successful delivery. Personnel can sign in with their email or username, must change that temporary password at first sign-in, and are then signed out to sign in again. Staff can request password recovery using an emailed verification code. Configure SMTP before inviting personnel or using email-based recovery. Registrar staff can access Overview, Requests, and read-only Students. Student write submissions are rejected server-side for staff accounts. The **Audit log** and printable **Reports** are administrator-only. Reports include daily/monthly/yearly request totals, status and document breakdowns, and active-period enrollment counts by course and year.

The user-based migration branch is `migrate_student_imports_existing.sql` for older databases that already use `users` and have a separate `students` table. `migrate_student_imports.sql` is an alternative legacy branch; do not run both. `migrate_personnel_accounts.sql` renames `admin_users` to `personnel_accounts`, but current sign-in, password changes, request history, and roster imports use `users`; that old path is not a supported upgrade path for the current application. Do not run it on the current database. `migrate_student_requests.sql` archives legacy payment values and then drops payment columns, so it must only be used on a matching old schema after a backup. `migrate_cleanup_unused_schema.sql` permanently drops legacy tables/columns and is not needed for installation; preserve it for historical reference and do not run it as routine cleanup. Never run migrations against the live database just to check them.

Create the first administrator through your approved database administration process. This project no longer includes a web-based initial-admin setup page. Database roles are `admin` and `registrar`; registrar accounts are presented as staff in the portal. Passwords are stored as PHP password hashes; never put admin passwords or database credentials in source files.

The public landing page is `index.php`; Admin/Staff sign-in is at `staff-login.php` and the protected portal is `admin.php`. Student roster import is available at `students.php`.

The CSV template is `assets/csv/student-import-template.csv`; it includes Student ID, first name, middle name, last name, email, and year level (1–4). Leave middle name blank when unavailable. Academic-period records for both semesters of the current calendar year’s academic period are created automatically when the Students or Course Management page is opened (for example, in 2027, 2027–2028 is added). In Course Management, administrators can open Academic periods, choose a period from the radio list, and use the single Activate button; only the selected active period validates currently enrolled students. The Students directory also shows only students with an active roster membership in the active period; inactive-period student information remains in history and is not shown as currently enrolled. In `students.php`, select a period and course, upload the CSV, review every row, and explicitly confirm before anything is written. The selected course and period apply to every imported row, and year levels must be available for that course. Imports are append-only: they do not replace prior courses, periods, profiles, enrollments, or request data. Inactive-period imports are staged and retained; activating that period makes its saved active roster eligible again. Only one academic period can be active, and no imported roster can validate a currently-enrolled request while its period is inactive. Invalid rows, repeated IDs, already-imported enrollments, and profile conflicts are recorded individually with their submitted row values. A row with conflicting profile details can be approved while preserving the existing profile; enrollment conflicts and Student ID mismatches require manual resolution. Import history shows imported/skipped/failed totals and can download a formula-safe CSV report for non-imported rows. Student ID may be blank only for a non-current record; active current enrollments still require it. Manual registrations support selected periods and enrollment classifications. Profiles can be searched and filtered by course/status/period, and viewed with preserved enrollment and request history. Manual registration is administrator-only; profile edits are audited and do not request the staff member’s password. Password confirmation is required for student deletion.

Student deletion is the only student workflow that asks for the current password again. Manual registration and CSV import are administrator-only and require an authenticated administrator session; imports also require explicit review and confirmation. Registrar staff can view student records but cannot submit student-record changes.

Import history is sorted and searchable by semester and course; each import's student list shows the original uploaded values and row outcomes. Delete and Move corrections apply only to the active semester, preserve student profiles and original import rows, and are recorded in correction history. Inactive semesters and their imports are preserved and read-only; administrators can reactivate an archived period to resume its saved roster. Only active memberships in the single active semester establish “currently enrolled” eligibility; alumni, dropped-out, and transferred-out requests continue through the former-student path without roster validation.

The integration checks in `tests/student_roster_integration.php` use MySQL temporary tables and do not write to persistent tables. Set `STUDENT_ROSTER_TEST_DSN` to an isolated MySQL test database DSN, optionally set `STUDENT_ROSTER_TEST_USER` and `STUDENT_ROSTER_TEST_PASSWORD`, then run `php tests/student_roster_integration.php`.

Install PHPMailer from the project folder with `composer install`. Configure `SMTP_HOST`, `SMTP_PORT`, `SMTP_USERNAME`, `SMTP_PASSWORD`, `SMTP_ENCRYPTION` (`tls` or `ssl`), and `SMTP_FROM_EMAIL` in the ignored `config.local.php` file before students request an email code. Do not commit or share SMTP credentials.

The public document list is at `request.php`, and the tracker shell is at `track.php`. After choosing a document, currently enrolled students look up their Student ID, confirm the matching details and masked email, then verify their email with a one-time code. Alumni, dropped-out, and transferred-out students enter their details and academic year attended, then verify the email address they provide. The current schema already includes guest requests, student-profile links, academic-record fields, verified-student name handling, and request retention. Do not rerun their migrations on a fresh install or on the current database. For an older database, first back it up and inspect which tables/columns are missing; then apply only the matching one-time migrations in dependency order: `migrate_student_requests.sql`, `migrate_guest_document_requests.sql`, `migrate_student_request_profile_links.sql`, `migrate_academic_record_request_details.sql`, `migrate_verified_student_request_names.sql`, and (if request retention is not present) `migrate_request_retention_archive.sql`. The student-request migration archives legacy payment values and drops payment columns, so it must only be used on a matching old schema. No payment is processed or recorded by this request flow; cashier receipts remain offline.

Verification codes submit automatically when all six digits are entered, pasted, or filled by the browser; there is no separate Verify button. For Transcript of Records and Honorable Dismissal requests, currently enrolled students verify their Student ID and then complete the academic-record form; their name comes from the verified student record. Alumni complete the same form without a Student ID and enter their name. The form uses the Philippine PSGC API for dependent location dropdowns and lists the latest 10 graduation years. When staff starts processing a request, the estimated release date is calculated from that document's configured processing weekdays; weekends are excluded, but public holidays, class suspensions, office closures, and other unforeseen circumstances may still cause delays. A successful request is saved as `SUBMITTED` with a unique reference. Email verification is remembered for currently enrolled students and their exact email address; updating the email requires a new verification.

Archived requests are excluded from active lists and public tracking; administrators can restore them during the 30-day window. Run `maintenance/purge_expired_requests.php` daily with the PHP CLI through Windows Task Scheduler, using the same Windows account/configuration that can access the database. The script is CLI-only, purges only requests whose 30-day retention has elapsed, and keeps a compact deletion/status audit without requester contact or address details.
